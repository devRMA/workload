### Finding 1 — the 2560 spend is 74, not 70; `design.md` §4.4's root-font model has a boundary error

`plan.md` T2's Done when states: "`PORT=3100 pnpm e2e tests/e2e/wide-viewport.spec.ts` **fails** on
the two new cases with a spend of **70** (2560) and **74** (3840)." Measured twice, in this tree,
against the production build: **74 at both 2560 and 3840** —
`C5 / 2560x1440 light — LR2a: bodyText 887 < surfaceRoot 961 − 32; chrome spend 74, 207 chars over 2
line boxes = 103.5 cpl`, byte-identical to the 3840 line except the viewport numbers. Reproduced
twice (two separate `pnpm e2e tests/e2e/wide-viewport.spec.ts` runs), both chromium, both `74`.

Root cause, checked directly against `app/globals.css:214-238` and confirmed with a throwaway
Playwright probe (`getComputedStyle(document.documentElement).fontSize`, deleted after use, never
committed): the root font-size steps at `@media (min-width: 120rem)` → `106.25%` and
`@media (min-width: 160rem)` → `112.5%`. `160rem` in a media feature resolves against the browser's
*initial* root font-size (16px), i.e. exactly **2560px** — not "somewhere past 2560." At a viewport
of exactly 2560px both media queries match, and the one declared later in the file
(`min-width: 160rem`) wins the cascade, so the root is **18px at 2560px**, identical to 3840px, not
17px as `design.md` §4.4 models. Measured directly: `width=2559 → 17px`, `width=2560 → 18px`,
`width=3840 → 18px`. The 17px band exists only for `[1920, 2559]`; the wide-viewport spec's own QHD
fixture (`{ width: 2560, ... }`) sits exactly on the boundary that resolves to 18px.

**What this developer cannot resolve alone:** `plan.md` T3's Done when states the remedy must land
